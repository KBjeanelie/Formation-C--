Plans d'Exécution & Indexation SQL Server

Découvrez la différence fondamentale entre les Clustered Index et Non-Clustered Index de SQL Server, et apprenez à lire les plans d'exécution graphiques de SSMS.

1. La grande différence : Clustered vs Non-Clustered Index

C'est une notion clé unique à SQL Server. Chaque table ne peut avoir qu'un seul Clustered Index (et une Primary Key crée automatiquement un Clustered Index).

  • Clustered Index : Les données de la table sont physiquement triées et stockées dans l'ordre de l'index. C'est comme trier les pages d'un livre. Accès ultra-rapide par cette colonne.
  • Non-Clustered Index : Une structure séparée qui contient les clés de recherche et un pointeur (la clé du Clustered Index) vers la ligne réelle. C'est comme l'index en fin de livre.
Heap vs Clustered Table : Si une table n'a pas de Primary Key (pas de Clustered Index), elle est appelée un "Heap" (tas). Les données sont en désordre total. SQL Server fait alors un "Table Scan" (équivalent du Full Table Scan).

Lire les plans d'exécution T-SQL

  • Dans SSMS : Cliquez sur "Inclure le plan d'exécution réel" (Ctrl+M) puis exécutez la requête. Un onglet graphique apparaît.
  • Table Scan / Clustered Index Scan : Lit tout (mauvais sur grande table).
  • Index Seek : Utilise l'index pour aller directement (excellent !).
  • Key Lookup : Après un Index Seek sur un Non-Clustered Index, SQL Server doit "sauter" vers la table pour récupérer les colonnes manquantes (coûteux).

2. Base de travail — Les Logs Serveur

USE master;
IF EXISTS(SELECT * FROM sys.databases WHERE name='logs_db') DROP DATABASE logs_db;
CREATE DATABASE logs_db; GO
USE logs_db; GO

CREATE TABLE server_logs (
    id INT IDENTITY(1,1) PRIMARY KEY,  -- Crée automatiquement un Clustered Index sur id
    ip_address NVARCHAR(15),
    endpoint NVARCHAR(100),
    status_code INT,
    response_time_ms INT,
    user_agent NVARCHAR(200),
    created_at DATETIME2
);
GO

3. Travaux Pratiques (10 exercices)

TP 01

Générer 2 millions de lignes (Boucle WHILE)

Créez une procédure qui insère 2 millions de lignes par lots (pour éviter un log de transaction trop grand).

▶ Voir la solution 
CREATE OR ALTER PROCEDURE dbo.generer_logs @n INT
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @i INT = 0, @batch INT = 10000;
    DECLARE @statuses TABLE (s INT);
    INSERT INTO @statuses VALUES(200),(201),(400),(401),(403),(404),(500);

    WHILE @i < @n
    BEGIN
        INSERT INTO server_logs(ip_address, endpoint, status_code, response_time_ms, user_agent, created_at)
        SELECT TOP(@batch)
            N'192.168.1.' + CAST(ABS(CHECKSUM(NEWID())) % 255 AS NVARCHAR),
            CHOOSE(ABS(CHECKSUM(NEWID())) % 5 + 1, N'/home',N'/api/users',N'/login',N'/dashboard',N'/api/data'),
            CHOOSE(ABS(CHECKSUM(NEWID())) % 7 + 1, 200,201,400,401,403,404,500),
            ABS(CHECKSUM(NEWID())) % 1000,
            CHOOSE(ABS(CHECKSUM(NEWID())) % 4 + 1, N'Mozilla',N'Chrome',N'Safari',N'curl'),
            DATEADD(DAY, -(ABS(CHECKSUM(NEWID())) % 365), GETDATE())
        FROM sys.objects a CROSS JOIN sys.objects b CROSS JOIN sys.objects c;
        SET @i = @i + @batch;
    END;
END;
GO

EXEC dbo.generer_logs 2000000;
SELECT COUNT(*) FROM server_logs;

-- Plan : Clustered Index Scan (lit tout l'index clusterisé, équivalent d'un Full Table Scan)
-- Logical reads: plusieurs milliers

TP 03

Non-Clustered Index et Index Seek

Créez un Non-Clustered Index sur ip_address. Relancez la requête. Le plan passe-t-il en "Index Seek" ? Observez le "Key Lookup".

▶ Voir la solution 
CREATE INDEX IX_logs_ip ON server_logs(ip_address);

SET STATISTICS IO ON;
SELECT * FROM server_logs WHERE ip_address = N'192.168.1.42';
-- Plan: Non-Clustered Index Seek → Key Lookup → Nested Loops
-- "Key Lookup" : SQL Server trouve les IDs via l'index, puis va chercher les autres colonnes dans le Clustered Index
TP 04

Éliminer le Key Lookup avec un Covering Index

Un Key Lookup est coûteux. Éliminez-le en incluant les colonnes du SELECT dans l'index via la clause INCLUDE.

▶ Voir la solution 
-- L'index INCLUDE stocke des colonnes supplémentaires dans le niveau feuille de l'index
-- sans qu'elles participent à l'arbre de recherche
CREATE INDEX IX_logs_ip_covering ON server_logs(ip_address)
INCLUDE (endpoint, status_code, response_time_ms, created_at);

SET STATISTICS IO ON;
SELECT ip_address, endpoint, status_code FROM server_logs WHERE ip_address = N'192.168.1.42';
-- Plan: Index Seek (sans Key Lookup !) → Toutes les données sont dans l'index
TP 05

Le piège du LIKE avec wildcard initial

Créez un index sur endpoint et testez pourquoi LIKE '%data' ne peut pas l'utiliser.

▶ Voir la solution 
CREATE INDEX IX_logs_endpoint ON server_logs(endpoint);

-- Index Seek possible :
SELECT * FROM server_logs WHERE endpoint LIKE N'/api%';

-- Clustered Index Scan (index inutilisable) :
SELECT * FROM server_logs WHERE endpoint LIKE N'%data';
-- SQL Server ne sait pas par où commencer l'index.
TP 06

Index Filtré (l'équivalent du Partial Index)

SQL Server supporte les index filtrés (Filtered Index) avec une clause WHERE. Créez un index uniquement sur les lignes d'erreur (status_code >= 400).

▶ Voir la solution 
CREATE INDEX IX_logs_erreurs ON server_logs(status_code)
WHERE status_code >= 400;  -- Index filtré !

-- SQL Server utilisera cet index léger pour les requêtes sur les erreurs :
SET STATISTICS IO ON;
SELECT * FROM server_logs WHERE status_code = 500;
-- Logical reads: beaucoup moins qu'un scan complet !
TP 07

Index Composé

Créez l'index optimal pour la requête WHERE status_code = 500 AND endpoint = '/login'.

▶ Voir la solution 
CREATE INDEX IX_logs_status_endpoint ON server_logs(status_code, endpoint);

SELECT * FROM server_logs WHERE status_code = 500 AND endpoint = N'/login';
-- Plan: Index Seek ✓
TP 08

Optimiser ORDER BY

Analysez la requête avec ORDER BY created_at DESC. L'opérateur "Sort" apparaît-il dans le plan ? Créez l'index pour l'éliminer.

▶ Voir la solution 
-- Avant (Sort dans le plan) :
SELECT TOP 10 * FROM server_logs ORDER BY created_at DESC;

-- Créer l'index trié :
CREATE INDEX IX_logs_date ON server_logs(created_at DESC);

-- Après : l'opérateur Sort disparaît du plan !
TP 09

Reconstruire les Index (Maintenance)

Après de nombreux INSERT/DELETE/UPDATE, les index se fragmentent. Utilisez ALTER INDEX pour les reconstruire ou les réorganiser.

▶ Voir la solution 
-- Voir la fragmentation de tous les index d'une table :
SELECT
    i.name AS index_name,
    s.avg_fragmentation_in_percent
FROM sys.dm_db_index_physical_stats(DB_ID(), OBJECT_ID('server_logs'), NULL, NULL, 'SAMPLED') s
JOIN sys.indexes i ON s.object_id = i.object_id AND s.index_id = i.index_id
WHERE s.avg_fragmentation_in_percent > 5
ORDER BY s.avg_fragmentation_in_percent DESC;

-- < 30% fragmenté : REORGANIZE (opération légère, en ligne)
ALTER INDEX IX_logs_ip ON server_logs REORGANIZE;

-- > 30% fragmenté : REBUILD (reconstruction complète)
ALTER INDEX IX_logs_ip ON server_logs REBUILD;

-- Reconstruire TOUS les index de la table :
ALTER INDEX ALL ON server_logs REBUILD;
TP 10

Missing Index Suggestions (Conseils automatiques)

SQL Server trace les opportunités d'index manquants. Après avoir exécuté vos requêtes lentes, consultez la DMV sys.dm_db_missing_index_details.

▶ Voir la solution 
-- Voir les index suggérés par SQL Server (trié par impact potentiel) :
SELECT TOP 10
    migs.avg_total_user_cost * migs.avg_user_impact * (migs.user_seeks + migs.user_scans) AS improvement_measure,
    mid.statement AS table_name,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns
FROM sys.dm_db_missing_index_group_stats migs
JOIN sys.dm_db_missing_index_groups mig ON migs.group_handle = mig.index_group_handle
JOIN sys.dm_db_missing_index_details mid ON mig.index_handle = mid.index_handle
ORDER BY improvement_measure DESC;

-- SQL Server vous dit exactement quels index créer pour améliorer les performances !
