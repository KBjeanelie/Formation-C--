Crash Test & Optimisation : Les Index

Générez des millions de lignes, analysez les plans d'exécution MySQL avec EXPLAIN et divisez vos temps de requête par 100 grâce aux index.

1. Comprendre EXPLAIN dans MySQL

La commande EXPLAIN (ou EXPLAIN ANALYZE dans MySQL 8.0.18+) affiche le plan d'exécution d'une requête. C'est votre outil de diagnostic principal.

EXPLAIN SELECT * FROM server_logs WHERE ip_address = '192.168.1.42';

Les colonnes clés à surveiller dans le résultat :

  • type : Le type de scan. Le meilleur au pire : system → const → eq_ref → ref → range → index → ALL (à éviter !)
  • key : L'index utilisé. NULL signifie aucun index utilisé.
  • rows : Estimation du nombre de lignes que MySQL va devoir lire.
  • Extra : Informations supplémentaires. "Using filesort" ou "Using temporary" sont des signaux d'alerte.
Différence avec PostgreSQL : MySQL utilise EXPLAIN seul (sans ANALYZE) pour voir le plan sans exécuter. EXPLAIN ANALYZE (MySQL 8+) exécute réellement et donne les temps.

2. Base de travail — Les Logs Serveur

CREATE DATABASE IF NOT EXISTS logs_db;
USE logs_db;
DROP TABLE IF EXISTS server_logs;

CREATE TABLE server_logs (
    id INT AUTO_INCREMENT PRIMARY KEY,
    ip_address VARCHAR(15),
    endpoint VARCHAR(100),
    status_code INT,
    response_time_ms INT,
    user_agent TEXT,
    created_at DATETIME
) ENGINE=InnoDB;

3. Travaux Pratiques (10 exercices)

TP 01

Générer 2 millions de lignes (Procédure de remplissage)

MySQL n'a pas de generate_series. Créez une procédure stockée qui insère 2 millions de lignes par boucle WHILE.

▶ Voir la solution 
DELIMITER //
CREATE PROCEDURE generer_logs(IN n INT)
BEGIN
    DECLARE i INT DEFAULT 0;
    DECLARE endpoints TEXT;
    WHILE i < n DO
        INSERT INTO server_logs (ip_address, endpoint, status_code, response_time_ms, user_agent, created_at)
        VALUES (
            CONCAT('192.168.1.', FLOOR(RAND()*255)),
            ELT(FLOOR(RAND()*5)+1, '/home','/api/users','/login','/dashboard','/api/data'),
            ELT(FLOOR(RAND()*7)+1, 200,201,400,401,403,404,500),
            FLOOR(RAND()*1000),
            ELT(FLOOR(RAND()*4)+1,'Mozilla Firefox','Google Chrome','Safari','curl/7.68.0'),
            DATE_SUB(NOW(), INTERVAL FLOOR(RAND()*365) DAY)
        );
        SET i = i + 1;
    END WHILE;
END //
DELIMITER ;

-- Désactiver l'autocommit pour la vitesse, puis insérer :
SET autocommit = 0;
CALL generer_logs(2000000);  -- ATTENTION: Cela peut prendre plusieurs minutes !
COMMIT;
SET autocommit = 1;

SELECT COUNT(*) FROM server_logs;
TP 02

Le Full Table Scan (Méthode lente)

Analysez la requête qui cherche les logs de l'IP 192.168.1.42 avec EXPLAIN. Quel est le type de scan ? Combien de lignes MySQL prévoit-il de lire ?

▶ Voir la solution 
EXPLAIN SELECT * FROM server_logs WHERE ip_address = '192.168.1.42';

-- Résultat attendu :
-- type: ALL (Full Table Scan)
-- key: NULL (aucun index utilisé)
-- rows: ~2000000 (MySQL doit TOUT lire)
TP 03

Créer l'index et observer le changement

Créez un index B-Tree sur ip_address. Relancez EXPLAIN et comparez le type de scan et le nombre de lignes estimées.

▶ Voir la solution 
CREATE INDEX idx_logs_ip ON server_logs(ip_address);

EXPLAIN SELECT * FROM server_logs WHERE ip_address = '192.168.1.42';

-- Résultat attendu :
-- type: ref (utilise l'index pour une valeur exacte)
-- key: idx_logs_ip
-- rows: ~8000 (au lieu de 2 000 000 !)
TP 04

Le piège du LIKE avec wildcard initial

Testez avec EXPLAIN pourquoi WHERE endpoint LIKE '%data' ne peut pas utiliser un index B-Tree standard. Expliquez le phénomène.

▶ Voir la solution 
CREATE INDEX idx_logs_endpoint ON server_logs(endpoint);

EXPLAIN SELECT * FROM server_logs WHERE endpoint LIKE '/api%';
-- type: range → L'index EST utilisé car on sait par où commencer.

EXPLAIN SELECT * FROM server_logs WHERE endpoint LIKE '%data';
-- type: ALL → L'index N'EST PAS utilisé.
-- Raison : Un index B-Tree trie les données de gauche à droite.
-- Si la wildcard est en premier, MySQL ne sait pas par où commencer l'index.
TP 05

Index sur expression avec les colonnes générées

Dans MySQL, on ne peut pas créer d'index sur une fonction directement. L'astuce est d'ajouter une colonne générée virtuelle basée sur l'expression, puis d'indexer cette colonne.

▶ Voir la solution 
-- Ajouter une colonne générée (virtuelle, pas stockée physiquement)
ALTER TABLE server_logs
ADD COLUMN user_agent_lower VARCHAR(255) AS (LOWER(user_agent)) VIRTUAL;

-- Créer l'index sur la colonne générée
CREATE INDEX idx_logs_lower_ua ON server_logs(user_agent_lower);

-- Maintenant cette requête peut utiliser l'index :
EXPLAIN SELECT * FROM server_logs WHERE LOWER(user_agent) = 'safari';
TP 06

Index Composite (Multi-colonnes)

Créez l'index optimal pour la requête WHERE status_code = 500 AND endpoint = '/login'. Vérifiez avec EXPLAIN que les deux colonnes sont utilisées.

▶ Voir la solution 
CREATE INDEX idx_logs_status_endpoint ON server_logs(status_code, endpoint);

EXPLAIN SELECT * FROM server_logs WHERE status_code = 500 AND endpoint = '/login';
-- type: ref, key: idx_logs_status_endpoint ✓
TP 07

Index Partiel (invisible dans MySQL)

MySQL ne supporte pas les index partiels avec une clause WHERE directement. Utilisez à la place la colonne générée ou un index fonctionnel. Indexez uniquement les erreurs en créant une colonne générée is_error.

▶ Voir la solution 
-- Colonne générée : 1 si erreur, NULL si succès (les index ignorent les NULL !)
ALTER TABLE server_logs
ADD COLUMN is_error TINYINT AS (IF(status_code >= 400, 1, NULL)) VIRTUAL;

CREATE INDEX idx_logs_errors ON server_logs(is_error);

-- Requête optimisée sur les erreurs :
EXPLAIN SELECT * FROM server_logs WHERE is_error = 1 AND status_code = 500;
-- MySQL utilisera l'index pour filtrer les erreurs d'abord.
TP 08

Covering Index (Index couvrant)

Créez un index sur (ip_address, status_code) et vérifiez avec EXPLAIN que la requête SELECT ip_address, status_code ... WHERE ip_address = '...' affiche "Using index" dans la colonne Extra (pas de lecture de table).

▶ Voir la solution 
CREATE INDEX idx_covering ON server_logs(ip_address, status_code);

EXPLAIN SELECT ip_address, status_code FROM server_logs
WHERE ip_address = '192.168.1.10';

-- Extra: Using index → MySQL a toutes les données dans l'index
-- Il ne lit pas la table physiquement ! C'est l'équivalent du Index Only Scan de PG.
TP 09

Optimiser ORDER BY

Analysez la requête ORDER BY created_at DESC LIMIT 10. L'Extra affiche "Using filesort" ? Créez l'index adapté pour l'éliminer.

▶ Voir la solution 
-- Avant (filesort) :
EXPLAIN SELECT * FROM server_logs ORDER BY created_at DESC LIMIT 10;
-- Extra: Using filesort (tri en mémoire/disque)

-- Créer l'index :
CREATE INDEX idx_logs_date ON server_logs(created_at DESC);

-- Après :
EXPLAIN SELECT * FROM server_logs ORDER BY created_at DESC LIMIT 10;
-- Extra: Backward index scan (ou vide) → Le tri a disparu !
TP 10

Auditer ses index inutilisés

MySQL 8.0 permet de rendre un index "invisible" pour tester s'il est réellement utile sans le supprimer. Testez cette fonctionnalité unique à MySQL.

▶ Voir la solution 
-- Voir tous les index d'une table :
SHOW INDEX FROM server_logs;

-- Rendre un index invisible (MySQL ne l'utilisera plus, mais il continue à se maintenir)
ALTER TABLE server_logs ALTER INDEX idx_logs_ip INVISIBLE;

-- Vérifier avec EXPLAIN qu'il n'est plus utilisé :
EXPLAIN SELECT * FROM server_logs WHERE ip_address = '192.168.1.42';

-- Si les performances ne changent pas, l'index était inutile → Supprimer :
DROP INDEX idx_logs_ip ON server_logs;

-- Sinon, le réactiver :
ALTER TABLE server_logs ALTER INDEX idx_logs_ip VISIBLE;
