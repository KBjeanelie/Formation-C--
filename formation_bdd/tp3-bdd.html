Séance 3 — 4 heures

Crash Test & Optimisation : Les Index

Comment une base de données gère-t-elle des millions de lignes ? Découvrez le fonctionnement des index B-Tree, analysez les plans d'exécution et apprenez à diviser vos temps de réponse par 100.

1. Comprendre l'Indexation et les Plans d'Exécution

Une table sans index est comme un livre sans sommaire. Pour trouver une information, la base de données doit lire chaque page depuis le début. C'est ce qu'on appelle un Sequential Scan (Seq Scan) ou Full Table Scan.

L'Index B-Tree

PostgreSQL utilise par défaut des arbres équilibrés (B-Tree) pour ses index. Ils permettent de trouver une valeur (ou une plage de valeurs) en un temps logarithmique O(log N) très rapide, en "sautant" directement aux bonnes pages de données (Index Scan).

Attention : Les index ralentissent les opérations d'écriture (INSERT, UPDATE, DELETE) car l'arbre doit être mis à jour. Il ne faut donc indexer que les colonnes fréquemment utilisées dans les clauses WHERE, JOIN ou ORDER BY.

Analyser les requêtes avec EXPLAIN

L'instruction EXPLAIN permet de demander à PostgreSQL comment il prévoit d'exécuter une requête (le Query Plan). EXPLAIN ANALYZE va plus loin en exécutant réellement la requête pour donner les temps précis.

EXPLAIN ANALYZE SELECT * FROM ma_table WHERE ma_colonne = 'valeur';

Ce qu'il faut surveiller dans le plan :

  • Seq Scan : Mauvais sur une grande table (parcourt tout).
  • Index Scan : Bon, utilise l'index et va chercher la ligne.
  • Index Only Scan : Excellent, l'index contient toutes les données demandées, pas besoin de lire la table.
  • Bitmap Heap Scan : Bon compromis utilisé quand l'index renvoie beaucoup de résultats.

Types d'index avancés

  • Index Composites : Sur plusieurs colonnes (ex: CREATE INDEX idx_a_b ON table (a, b)). Utile si les deux colonnes sont souvent interrogées ensemble.
  • Index Partiels : Seulement sur une partie des données (ex: WHERE status = 'actif'). Gagne de l'espace disque.
  • Index sur expression : Ex: CREATE INDEX idx_lower_email ON users(LOWER(email)).

2. Base de travail — Les Logs Serveur

Nous allons générer une table massive pour ressentir la douleur d'un Seq Scan.

DROP TABLE IF EXISTS server_logs CASCADE;

CREATE TABLE server_logs (
    id SERIAL PRIMARY KEY,
    ip_address VARCHAR(15),
    endpoint VARCHAR(100),
    status_code INT,
    response_time_ms INT,
    user_agent TEXT,
    created_at TIMESTAMP
);

3. Travaux Pratiques (10 exercices)

TP 01

Générer 2 millions de lignes (Le Crash Test)

Utilisez generate_series pour insérer 2 000 000 de fausses lignes dans server_logs. (L'exécution peut prendre 10 à 30 secondes selon votre machine).

▶ Voir la solution 
INSERT INTO server_logs (ip_address, endpoint, status_code, response_time_ms, user_agent, created_at)
SELECT 
    '192.168.1.' || (random() * 255)::int,
    (ARRAY['/home', '/api/users', '/login', '/dashboard', '/api/data'])[ceil(random()*5)],
    (ARRAY[200, 201, 400, 401, 403, 404, 500])[ceil(random()*7)],
    (random() * 1000)::int,
    (ARRAY['Mozilla Firefox', 'Google Chrome', 'Safari', 'curl/7.68.0'])[ceil(random()*4)],
    NOW() - (random() * interval '365 days')
FROM generate_series(1, 2000000);

-- Vérifiez le nombre de lignes :
SELECT count(*) FROM server_logs;
TP 02

Le Seq Scan (L'analyse de base)

Trouvez tous les logs de l'IP 192.168.1.42. Utilisez EXPLAIN ANALYZE pour voir combien de temps PostgreSQL met pour trouver les résultats. Quel type de scan est utilisé ?

▶ Voir la solution 
EXPLAIN ANALYZE 
SELECT * FROM server_logs WHERE ip_address = '192.168.1.42';

-- Résultat attendu :
-- -> Seq Scan on server_logs
-- Execution Time: XXX ms (souvent > 150ms)
TP 03

L'Index Simple (La révélation)

Créez un index B-Tree sur la colonne ip_address. Relancez la requête précédente avec EXPLAIN ANALYZE. Observez la différence de plan et de temps.

▶ Voir la solution 
-- Création de l'index (prend un peu de temps à construire)
CREATE INDEX idx_logs_ip ON server_logs(ip_address);

-- Nouvelle analyse :
EXPLAIN ANALYZE 
SELECT * FROM server_logs WHERE ip_address = '192.168.1.42';

-- Résultat attendu :
-- -> Bitmap Index Scan on idx_logs_ip
-- -> Bitmap Heap Scan on server_logs
-- Execution Time: X ms (souvent < 5ms, l'amélioration est drastique !)
TP 04

Le piège du LIKE et les Index

Faites un EXPLAIN ANALYZE pour chercher les requêtes dont le endpoint commence par /api%, puis une autre pour ceux qui se terminent par %data. Quel est le problème avec le joker % au début ?

▶ Voir la solution 
-- Requête 1 (Wildcard à la fin) :
EXPLAIN ANALYZE SELECT count(*) FROM server_logs WHERE endpoint LIKE '/api%';
-- Si on avait un index standard sur endpoint, il pourrait être utilisé (Index Scan).

-- Requête 2 (Wildcard au début) :
EXPLAIN ANALYZE SELECT count(*) FROM server_logs WHERE endpoint LIKE '%data';
-- PostgreSQL est OBLIGÉ de faire un Seq Scan.
-- Un index B-Tree trie de gauche à droite (comme l'annuaire). 
-- Si on cherche "%data", l'index ne sert à rien car on ne connait pas la première lettre.
TP 05

Index sur Expression (LOWER)

Parfois on cherche sans se soucier de la casse : WHERE LOWER(user_agent) = 'safari'. Faites le test, créez l'index adapté, et relancez.

▶ Voir la solution 
-- Sans index (Seq Scan) :
EXPLAIN ANALYZE SELECT * FROM server_logs WHERE LOWER(user_agent) = 'safari';

-- Un index classique sur user_agent ne marchera PAS ici, car on applique une fonction.
-- Il faut indexer le RÉSULTAT de la fonction :
CREATE INDEX idx_logs_lower_ua ON server_logs(LOWER(user_agent));

-- Avec index (Bitmap Heap Scan / Index Scan) :
EXPLAIN ANALYZE SELECT * FROM server_logs WHERE LOWER(user_agent) = 'safari';
TP 06

L'Index Composite (Multi-colonnes)

Vous cherchez souvent les erreurs 500 sur un endpoint spécifique : WHERE status_code = 500 AND endpoint = '/login'. Créez l'index idéal pour cette requête précise.

▶ Voir la solution 
-- L'index composite
CREATE INDEX idx_logs_status_endpoint ON server_logs(status_code, endpoint);

-- Test :
EXPLAIN ANALYZE 
SELECT * FROM server_logs WHERE status_code = 500 AND endpoint = '/login';

-- L'ordre des colonnes dans l'index compte !
-- (status_code, endpoint) est très efficace pour WHERE status_code=X AND endpoint=Y
-- ou WHERE status_code=X tout court.
-- MAIS il sera inefficace pour WHERE endpoint=Y tout court (il faut un autre index).
TP 07

L'Index Partiel (Gain de place)

Vous avez souvent besoin de retrouver uniquement les logs d'erreur (status_code >= 400). Les 200 OK ne vous intéressent pas dans vos recherches. Créez un index qui ne pèsera pas lourd sur le disque.

▶ Voir la solution 
-- L'index partiel ne stocke que les lignes vérifiant la condition
CREATE INDEX idx_logs_erreurs ON server_logs(status_code) WHERE status_code >= 400;

-- Test :
EXPLAIN ANALYZE SELECT * FROM server_logs WHERE status_code = 500;
-- PostgreSQL utilisera cet index partiel.

-- Test 2 :
EXPLAIN ANALYZE SELECT * FROM server_logs WHERE status_code = 200;
-- PostgreSQL fera un Seq Scan car il sait que les "200" ne sont pas dans l'index partiel.
TP 08

Index Only Scan (Le Graal)

Créez un index qui permet à la requête SELECT ip_address, status_code FROM server_logs WHERE ip_address = '192.168.1.10'; de s'exécuter sans même lire la table.

▶ Voir la solution 
-- Si l'index contient TOUTES les colonnes demandées dans le SELECT,
-- PostgreSQL n'a pas besoin de consulter la table.

CREATE INDEX idx_logs_ip_status ON server_logs(ip_address, status_code);

EXPLAIN ANALYZE 
SELECT ip_address, status_code FROM server_logs WHERE ip_address = '192.168.1.10';

-- Résultat attendu :
-- -> Index Only Scan using idx_logs_ip_status on server_logs
TP 09

Le tri avec ORDER BY

Les index stockent les données triées. Utilisez EXPLAIN ANALYZE sur ORDER BY created_at DESC LIMIT 10. Créez l'index adéquat pour supprimer l'étape coûteuse de tri (Sort ou Top-N heapsort) dans le plan.

▶ Voir la solution 
-- Avant index (Seq Scan + Top-N heapsort) :
EXPLAIN ANALYZE SELECT * FROM server_logs ORDER BY created_at DESC LIMIT 10;

-- L'index :
CREATE INDEX idx_logs_date ON server_logs(created_at DESC);

-- Après index (Index Scan Backward ou Forward) :
EXPLAIN ANALYZE SELECT * FROM server_logs ORDER BY created_at DESC LIMIT 10;
-- Le tri a disparu du plan car les données sont déjà triées dans l'index !
TP 10

Auditer ses index

Les index coûtent cher en écriture. Comment savoir s'ils sont réellement utilisés par PostgreSQL ? Interrogez la vue système pg_stat_user_indexes.

▶ Voir la solution 
SELECT 
    relname AS table_name, 
    indexrelname AS index_name, 
    idx_scan AS number_of_scans,
    idx_tup_read AS tuples_read,
    idx_tup_fetch AS tuples_fetched
FROM pg_stat_user_indexes 
WHERE relname = 'server_logs'
ORDER BY idx_scan DESC;

-- Si idx_scan = 0, cela signifie que votre index n'a JAMAIS été utilisé
-- depuis le dernier redémarrage des stats. Vous pouvez probablement le supprimer (DROP INDEX) !
