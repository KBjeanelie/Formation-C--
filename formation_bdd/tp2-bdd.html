Séance 2

Sécurité & Transactions

Gérez les accès à vos données et assurez-vous de l'intégrité de vos opérations critiques grâce aux principes ACID.

Introduction (Théorie - 15 min)

Une transaction est une séquence d'opérations exécutées comme un seul bloc. Soit TOUT réussit (COMMIT), soit TOUT est annulé (ROLLBACK).

La sécurité passe par la création de ROLES (utilisateurs) et l'attribution de droits (GRANT / REVOKE).

TP 1 : Création d'un Rôle de Lecture

Objectif : Créer un utilisateur "stagiaire" avec le mot de passe "1234", qui ne peut faire que des SELECT sur la table produits.
Voir la solution 
-- Création du rôle avec droit de connexion
CREATE ROLE stagiaire WITH LOGIN PASSWORD '1234';

-- Donner le droit d'utiliser le schéma public
GRANT USAGE ON SCHEMA public TO stagiaire;

-- Donner le droit de SELECT uniquement sur produits
GRANT SELECT ON produits TO stagiaire;

-- Essayez de vous connecter en tant que 'stagiaire' et tentez un UPDATE !

TP 2 : Le Virement Bancaire (Transactions)

Objectif : Créer une table comptes (id, solde). Faire un virement de 100€ du compte A vers le compte B dans un bloc transactionnel. Provoquer une erreur pour voir le ROLLBACK en action.
Voir la solution 
CREATE TABLE comptes (id INT PRIMARY KEY, solde DECIMAL);
INSERT INTO comptes VALUES (1, 500), (2, 500);

-- Début de la transaction
BEGIN;

-- 1. Retirer à A
UPDATE comptes SET solde = solde - 100 WHERE id = 1;

-- 2. Ajouter à B
UPDATE comptes SET solde = solde + 100 WHERE id = 2;

-- Si tout est ok :
COMMIT;

-- Test d'erreur :
BEGIN;
UPDATE comptes SET solde = solde - 1000 WHERE id = 1;
-- Simulation d'une coupure serveur ici... on annule :
ROLLBACK;
-- Le solde est revenu à son état initial !

TP 3 : Simulation d'un Deadlock (Verrou mortel)

Objectif : Simuler deux utilisateurs qui tentent de modifier les mêmes ressources en croisé, bloquant ainsi la base. (Ouvrez 2 terminaux / fenêtres psql).
Voir la solution

Dans le Terminal 1 :

BEGIN;
UPDATE comptes SET solde = solde + 10 WHERE id = 1;

Dans le Terminal 2 :

BEGIN;
UPDATE comptes SET solde = solde + 10 WHERE id = 2;

De retour dans le Terminal 1 :

UPDATE comptes SET solde = solde - 10 WHERE id = 2;
-- (Ça bloque, il attend que le T2 finisse)

Dans le Terminal 2 :

UPDATE comptes SET solde = solde - 10 WHERE id = 1;
-- ERREUR ! PostgreSQL détecte le deadlock et tue l'une des transactions.
