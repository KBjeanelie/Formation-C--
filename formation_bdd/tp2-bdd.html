Transactions ACID & Sécurité PostgreSQL

Garantissez l'intégrité des données sous haute charge et protégez votre base avec un système de droits granulaires. Deux piliers indispensables en production.

1. Les Transactions et le modèle ACID

Une transaction est un ensemble d'opérations SQL traitées comme une unité indivisible. En PostgreSQL, toute requête est implicitement dans une transaction. Vous pouvez les contrôler manuellement avec BEGIN, COMMIT et ROLLBACK.

A

Atomicité

Tout ou rien. Si une étape échoue, l'ensemble de la transaction est annulé.

C

Cohérence

La base passe d'un état valide à un autre état valide. Les contraintes sont toujours respectées.

I

Isolation

Les transactions concurrentes ne se "voient" pas mutuellement jusqu'au COMMIT.

D

Durabilité

Une fois commitée, la transaction est persistée même en cas de crash serveur.

Anatomie d'une transaction

BEGIN;  -- Ouvre la transaction

  UPDATE comptes SET solde = solde - 200 WHERE id = 1;  -- Étape 1
  UPDATE comptes SET solde = solde + 200 WHERE id = 2;  -- Étape 2

COMMIT;  -- Valide définitivement les deux changements

-- Si une erreur survient entre les deux UPDATE :
ROLLBACK;  -- Annule tout, comme si rien ne s'était passé

Les SAVEPOINT : annulation partielle

Un SAVEPOINT permet de définir des points de restauration intermédiaires à l'intérieur d'une transaction longue, sans annuler toute la transaction.

BEGIN;
  INSERT INTO logs (msg) VALUES ('Étape 1 OK');
  SAVEPOINT sp1;

  INSERT INTO logs (msg) VALUES ('Étape 2 OK');
  SAVEPOINT sp2;

  -- Une erreur survient ici...
  ROLLBACK TO sp1;  -- On revient après l'étape 1 seulement
  -- sp2 est détruit, mais sp1 existe encore

COMMIT;  -- Seule l'étape 1 est commitée

Niveaux d'isolation

PostgreSQL propose 4 niveaux d'isolation, contrôlant ce qu'une transaction peut "voir" des autres :

-- Défaut : READ COMMITTED (voit uniquement les données commitées)
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- Plus strict : REPEATABLE READ (chaque lecture retourne le même résultat)
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Le plus strict : SERIALIZABLE (transactions exécutées comme si elles étaient séquentielles)
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
⚠️ Le Deadlock (Verrou mortel) : Deux transactions se bloquent mutuellement en attendant que l'autre libère une ressource. PostgreSQL les détecte automatiquement et en tue une pour débloquer la situation. La solution est d'accéder toujours aux ressources dans le même ordre.

2. Sécurité : Rôles et Privilèges

PostgreSQL utilise un système de ROLES (qui remplacent à la fois les utilisateurs et les groupes). Un rôle peut se connecter, posséder des objets, et avoir des privilèges sur d'autres objets.

Créer et gérer des rôles

-- Créer un rôle utilisateur (avec login)
CREATE ROLE app_user WITH LOGIN PASSWORD 'motdepasse_fort';

-- Créer un rôle groupe (sans login, pour grouper les droits)
CREATE ROLE lecteurs;

-- Ajouter un utilisateur à un groupe
GRANT lecteurs TO app_user;

-- Supprimer un rôle
DROP ROLE app_user;

GRANT : donner des droits

-- Droits sur une table spécifique
GRANT SELECT ON produits TO lecteurs;
GRANT SELECT, INSERT, UPDATE ON commandes TO app_user;

-- Droits sur toutes les tables d'un schéma
GRANT SELECT ON ALL TABLES IN SCHEMA public TO lecteurs;

-- Permettre à un rôle d'accorder ses droits à d'autres (WITH GRANT OPTION)
GRANT SELECT ON produits TO manager WITH GRANT OPTION;

-- Droit d'utiliser le schéma (obligatoire en pratique)
GRANT USAGE ON SCHEMA public TO lecteurs;

REVOKE : retirer des droits

REVOKE INSERT ON commandes FROM app_user;
REVOKE ALL ON produits FROM lecteurs;

Row Level Security (RLS) — Sécurité niveau ligne

Une fonctionnalité avancée de PostgreSQL qui permet de filtrer automatiquement les lignes qu'un utilisateur peut voir ou modifier, sans changer les requêtes.

-- Activer RLS sur la table
ALTER TABLE commandes ENABLE ROW LEVEL SECURITY;

-- Politique : un utilisateur ne voit que ses propres commandes
CREATE POLICY user_isolation ON commandes
    USING (client_id = current_setting('app.current_user_id')::INT);

3. Base de travail — Système Bancaire

Exécutez ce script avant de démarrer les TPs :

DROP TABLE IF EXISTS comptes, virements, journal_erreurs CASCADE;

CREATE TABLE comptes (
    id SERIAL PRIMARY KEY,
    titulaire VARCHAR(100) NOT NULL,
    solde DECIMAL(12,2) DEFAULT 0 CHECK (solde >= 0),
    type_compte VARCHAR(20) DEFAULT 'courant'
);

CREATE TABLE virements (
    id SERIAL PRIMARY KEY,
    compte_source INT REFERENCES comptes(id),
    compte_dest INT REFERENCES comptes(id),
    montant DECIMAL(12,2),
    statut VARCHAR(20) DEFAULT 'en_attente',
    effectue_le TIMESTAMP DEFAULT now()
);

CREATE TABLE journal_erreurs (
    id SERIAL PRIMARY KEY,
    message TEXT,
    contexte TEXT,
    survenu_le TIMESTAMP DEFAULT now()
);

    ('Clara Simon', 5000.00, 'epargne'),

4. Travaux Pratiques (10 exercices)

TP 01

Transaction simple : Virement sécurisé

Effectuez un virement de 200€ du compte d'Alice (id=1) vers Bob (id=2) dans un bloc transactionnel manuel. Vérifiez les soldes avant et après.

▶ Voir la solution 
-- Avant
SELECT id, titulaire, solde FROM comptes WHERE id IN (1,2);

BEGIN;
  UPDATE comptes SET solde = solde - 200 WHERE id = 1;
  UPDATE comptes SET solde = solde + 200 WHERE id = 2;
COMMIT;

-- Après
SELECT id, titulaire, solde FROM comptes WHERE id IN (1,2);
-- Alice: 1300€  |  Bob: 500€
TP 02

ROLLBACK : Simuler un crash

Ouvrez une transaction, débitez 100€ d'Alice, puis utilisez ROLLBACK. Vérifiez que son solde est inchangé.

▶ Voir la solution 
SELECT solde FROM comptes WHERE id = 1; -- 1300€

BEGIN;
  UPDATE comptes SET solde = solde - 100 WHERE id = 1;
  SELECT solde FROM comptes WHERE id = 1; -- 1200€ (visible dans cette session)
ROLLBACK;

SELECT solde FROM comptes WHERE id = 1; -- 1300€ : annulation totale !
TP 03

Procédure transactionnelle : Virement avec validation

Créez une procédure effectuer_virement(source, dest, montant) qui : vérifie que le solde source est suffisant, effectue le virement, enregistre l'opération dans virements, et lève une exception en cas de fonds insuffisants.

▶ Voir la solution 
CREATE OR REPLACE PROCEDURE effectuer_virement(
    p_source INT, p_dest INT, p_montant DECIMAL
) AS $$
DECLARE
    v_solde DECIMAL;
BEGIN
    IF p_montant <= 0 THEN
        RAISE EXCEPTION 'Le montant doit être positif';
    END IF;

    SELECT solde INTO v_solde FROM comptes WHERE id = p_source FOR UPDATE;

    IF v_solde < p_montant THEN
        INSERT INTO journal_erreurs(message, contexte)
        VALUES ('Fonds insuffisants', format('Compte %s: solde=%.2f, demande=%.2f', p_source, v_solde, p_montant));
        RAISE EXCEPTION 'Fonds insuffisants (solde: %.2f€, demandé: %.2f€)', v_solde, p_montant;
    END IF;

    UPDATE comptes SET solde = solde - p_montant WHERE id = p_source;
    UPDATE comptes SET solde = solde + p_montant WHERE id = p_dest;

    INSERT INTO virements(compte_source, compte_dest, montant, statut)
    VALUES (p_source, p_dest, p_montant, 'effectue');

    RAISE NOTICE 'Virement de %.2f€ : compte % → compte % OK', p_montant, p_source, p_dest;
END;
$$ LANGUAGE plpgsql;

-- Tests :
CALL effectuer_virement(1, 2, 50);    -- OK
CALL effectuer_virement(5, 1, 100);   -- Doit échouer (David, solde 0)
SELECT * FROM virements;
SELECT * FROM journal_erreurs;
TP 04

SAVEPOINT : Transaction à étapes multiples

Simulez une série de virements dans une seule transaction. Si l'un échoue, revenez au point précédent grâce à un SAVEPOINT, sans annuler les virements réussis.

▶ Voir la solution 
BEGIN;
  CALL effectuer_virement(1, 2, 30);
  SAVEPOINT apres_premier;

  CALL effectuer_virement(3, 1, 100);
  SAVEPOINT apres_deuxieme;

  -- Ce virement va échouer (David n'a pas de solde)
  BEGIN
    CALL effectuer_virement(5, 2, 500);
  EXCEPTION WHEN OTHERS THEN
    RAISE NOTICE 'Virement 3 échoué: %, retour au savepoint', SQLERRM;
    ROLLBACK TO apres_deuxieme;
  END;

COMMIT;

SELECT id, titulaire, solde FROM comptes ORDER BY id;
TP 05

Créer des rôles avec droits limités

Créez un rôle conseiller qui peut lire tous les comptes mais ne peut ni modifier les soldes ni supprimer de lignes. Vérifiez en tentant un UPDATE.

▶ Voir la solution 
CREATE ROLE conseiller WITH LOGIN PASSWORD 'conseiller123';

GRANT USAGE ON SCHEMA public TO conseiller;
GRANT SELECT ON comptes, virements TO conseiller;
-- Note : pas de GRANT UPDATE ni DELETE

-- Pour tester, connectez-vous en tant que conseiller :
-- psql -U conseiller -d votre_base

-- Depuis une session conseiller :
SELECT * FROM comptes;  -- OK
UPDATE comptes SET solde = 99999 WHERE id = 1;  -- ERREUR: permission denied
TP 06

Rôle applicatif avec droits sur procédures uniquement

Créez un rôle app_banking qui peut uniquement exécuter la procédure effectuer_virement, mais sans accès direct aux tables. Ainsi l'application ne peut pas faire des UPDATE arbitraires.

▶ Voir la solution 
CREATE ROLE app_banking WITH LOGIN PASSWORD 'banking_secret!';

GRANT USAGE ON SCHEMA public TO app_banking;
-- Pas de GRANT sur les tables !
GRANT EXECUTE ON PROCEDURE effectuer_virement(INT, INT, DECIMAL) TO app_banking;

-- L'app peut seulement :
CALL effectuer_virement(1, 2, 10);  -- OK si exécuté avec SECURITY DEFINER

-- Mais ne peut pas :
UPDATE comptes SET solde = 0;  -- ERREUR: permission denied

-- ASTUCE : ajoutez SECURITY DEFINER à la procédure pour qu'elle s'exécute
-- avec les droits de son créateur (le superuser), pas de l'appelant.
-- Cela sécurise complètement l'accès aux données.
TP 07

Trigger : Bloquer les virements suspects

Créez un trigger BEFORE INSERT sur virements qui bloque tout virement supérieur à 10 000€ et le journalise dans journal_erreurs.

▶ Voir la solution 
CREATE OR REPLACE FUNCTION bloquer_gros_virement()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.montant > 10000 THEN
        INSERT INTO journal_erreurs(message, contexte)
        VALUES (
            'Virement bloqué : montant excessif',
            format('Montant: %.2f€ | Source: %s | Dest: %s | User: %s',
                   NEW.montant, NEW.compte_source, NEW.compte_dest, current_user)
        );
        RAISE EXCEPTION 'Virement de %.2f€ refusé: dépasse le plafond de 10 000€', NEW.montant;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_virement_suspect
BEFORE INSERT ON virements
FOR EACH ROW EXECUTE FUNCTION bloquer_gros_virement();

-- Test :
INSERT INTO virements(compte_source, compte_dest, montant)
VALUES (4, 1, 15000);  -- Doit être bloqué
SELECT * FROM journal_erreurs;
TP 08

Isolation : Observer la lecture sale (Read Committed)

Simulez deux sessions concurrentes. Dans la session A, ouvrez une transaction et modifiez un solde sans committer. Dans la session B, lisez le même solde. Observez ce que B peut voir (ou pas).

▶ Voir la solution 
-- === SESSION A (ouvrez un premier psql) ===
BEGIN;
UPDATE comptes SET solde = 99999 WHERE id = 1;
-- NE PAS COMMITTER encore !

-- === SESSION B (ouvrez un second psql) ===
SELECT solde FROM comptes WHERE id = 1;
-- Résultat : 1300€ (l'ancienne valeur)
-- PostgreSQL utilise READ COMMITTED par défaut :
-- la session B ne voit PAS les données non-commitées de A.

-- === SESSION A ===
COMMIT;

-- === SESSION B ===
SELECT solde FROM comptes WHERE id = 1;
-- Résultat : 99999€ (maintenant visible après le COMMIT)

-- Remise en état :
UPDATE comptes SET solde = 1300 WHERE id = 1;
TP 09

Fonction sécurisée : Rapport solde masqué

Créez une fonction rapport_compte(p_id INT) avec l'attribut SECURITY DEFINER accessible au rôle conseiller. Elle retourne le titulaire et le solde masqué (ex: "****500.00€") pour protéger l'information sensible.

▶ Voir la solution 
CREATE OR REPLACE FUNCTION rapport_compte(p_id INT)
RETURNS TABLE(titulaire TEXT, solde_masque TEXT)
SECURITY DEFINER  -- S'exécute avec les droits du créateur
AS $$
BEGIN
    RETURN QUERY
    SELECT
        c.titulaire::TEXT,
        ('****' || RIGHT(c.solde::TEXT, 6))::TEXT AS solde_masque
    FROM comptes c
    WHERE c.id = p_id;
END;
$$ LANGUAGE plpgsql;

GRANT EXECUTE ON FUNCTION rapport_compte(INT) TO conseiller;

-- Test :
SELECT * FROM rapport_compte(1);
-- titulaire: Alice Martin | solde_masque: ****300.00
TP 10

Bilan : Procédure de clôture mensuelle

Créez une procédure cloture_mensuelle() qui : (1) applique un intérêt de 2% sur tous les comptes épargne, (2) prélève des frais de tenue de 5€ sur les comptes courants en positif, (3) enregistre un rapport dans journal_erreurs avec le nombre de comptes traités. Tout doit être dans une seule transaction.

▶ Voir la solution 
CREATE OR REPLACE PROCEDURE cloture_mensuelle()
AS $$
DECLARE
    nb_epargne INT := 0;
    nb_courant INT := 0;
BEGIN
    -- 1. Intérêts sur comptes épargne
    UPDATE comptes
    SET solde = ROUND(solde * 1.02, 2)
    WHERE type_compte = 'epargne';
    GET DIAGNOSTICS nb_epargne = ROW_COUNT;

    -- 2. Frais sur comptes courants
    UPDATE comptes
    SET solde = solde - 5
    WHERE type_compte = 'courant' AND solde > 0;
    GET DIAGNOSTICS nb_courant = ROW_COUNT;

    -- 3. Rapport
    INSERT INTO journal_erreurs(message, contexte)
    VALUES (
        'CLOTURE MENSUELLE OK',
        format('%s comptes épargne (intérêts +2%%), %s comptes courants (frais -5€)', nb_epargne, nb_courant)
    );

    RAISE NOTICE 'Clôture terminée: % épargne, % courants traités', nb_epargne, nb_courant;
END;
$$ LANGUAGE plpgsql;

-- Exécution :
CALL cloture_mensuelle();
SELECT id, titulaire, solde, type_compte FROM comptes ORDER BY type_compte;
SELECT message, contexte FROM journal_erreurs ORDER BY id DESC LIMIT 1;
