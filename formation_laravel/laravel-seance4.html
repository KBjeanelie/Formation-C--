01

Objectifs de la séance

  • Mettre en place l'authentification (inscription, connexion, déconnexion) avec Laravel Breeze.
  • Protéger des routes avec des middlewares.
  • Exposer une API REST en JSON, avec des routes et contrôleurs dédiés.
  • Sécuriser une API avec un jeton d'accès (Sanctum).
  • Livrer un mini-projet complet, entièrement dockerisé, qui réunit toutes les notions des 4 séances.
02

Authentification avec Laravel Breeze

Breeze installe en quelques commandes des pages d'inscription, de connexion et un tableau de bord protégé, avec un code simple à lire et à personnaliser.
docker compose exec app composer require laravel/breeze --dev
docker compose exec app php artisan breeze:install blade

Breeze génère des assets front-end (CSS/JS) qui doivent être compilés avec Node — à ajouter au Dockerfile de la séance 1 :

RUN apt-get update && apt-get install -y nodejs npm
docker compose exec app npm install
docker compose exec app npm run build
docker compose exec app php artisan migrate

Une fois installé, Breeze fournit automatiquement les routes /register, /login, /logout et un /dashboard protégé.

Pourquoi Breeze plutôt qu'un système d'authentification écrit à la main : hacher les mots de passe, gérer les sessions, se protéger contre les attaques par force brute — Breeze applique déjà les bonnes pratiques de sécurité de Laravel, plutôt que de laisser chaque étudiant réinventer un mécanisme sensible avec ses propres failles potentielles.
03

Protéger des routes avec un middleware

// routes/web.php
Route::middleware('auth')->group(function () {
    Route::resource('livres', LivreController::class);
});

Toutes les routes du groupe exigent désormais un utilisateur connecté ; un visiteur non authentifié est automatiquement redirigé vers /login.

Pourquoi grouper avec middleware('auth') plutôt que de vérifier Auth::check() dans chaque méthode : la règle "connecté obligatoire" est déclarée à un seul endroit, pour toutes les routes du groupe — impossible d'oublier la vérification sur une nouvelle méthode ajoutée plus tard au contrôleur.
04

API REST

Une API REST expose les données en JSON, pour qu'une application mobile, un autre service, ou une frontend séparé (React, Vue...) puisse les consommer sans passer par les vues Blade.
docker compose exec app php artisan make:controller Api/LivreController --api
// routes/api.php
use App\Http\Controllers\Api\LivreController;

Route::apiResource('livres', LivreController::class);
// app/Http/Controllers/Api/LivreController.php
public function index()
{
    return Livre::all();
}

public function store(Request $request)
{
    $donnees = $request->validate([
        'titre' => 'required|max:255',
        'auteur' => 'required|max:255',
    ]);

    return Livre::create($donnees);
}
Pourquoi routes/api.php et un contrôleur séparés de routes/web.php : une API ne renvoie jamais de HTML ni de vue Blade — la séparer évite de mélanger deux logiques de réponse différentes (JSON pour l'API, pages complètes pour le web) dans les mêmes contrôleurs.

Sécuriser l'API avec Sanctum

docker compose exec app php artisan install:api
// routes/api.php
Route::middleware('auth:sanctum')->group(function () {
    Route::apiResource('livres', LivreController::class);
});

Un client doit alors envoyer un jeton dans l'en-tête de chaque requête :

curl -H "Authorization: Bearer TOKEN_ICI" http://localhost:8000/api/livres
Piège fréquent : confondre l'authentification par session (auth, utilisée pour les pages web avec cookies de navigateur) et l'authentification par jeton (auth:sanctum, utilisée pour une API consommée par un client externe qui n'a pas de cookie de session).
05

Exercices pratiques

À réaliser avant le mini-projet final, dans le même environnement Docker que les séances précédentes.
Ex. 1

Installer Breeze et vérifier l'inscription

échauffement

Installer Breeze sur le projet, créer un compte via /register, se déconnecter, se reconnecter via /login, et vérifier que /dashboard redirige vers /login quand on n'est pas connecté.

Voir la solution

Aucun code à écrire — l'exercice consiste à valider chaque étape :

  1. docker compose exec app composer require laravel/breeze --dev
  2. docker compose exec app php artisan breeze:install blade
  3. docker compose exec app npm install && npm run build
  4. docker compose exec app php artisan migrate
  5. Ouvrir /register, créer un compte, être redirigé vers /dashboard.
  6. Se déconnecter, essayer /dashboard directement : redirection vers /login attendue.
Ex. 2

Protéger le CRUD des cours

facile

Reprendre le Route::resource('cours', ...) de la séance 3 et le placer dans un groupe middleware('auth'), pour que seule une personne connectée puisse gérer les cours.

Voir la solution 
// routes/web.php
Route::middleware('auth')->group(function () {
    Route::resource('cours', CoursController::class);
});
Ex. 3

API publique en lecture seule

intermédiaire

Créer une route API GET /api/cours qui retourne la liste des cours en JSON, accessible sans authentification (pour un futur site vitrine qui affiche les cours disponibles), en gardant la création/modification/suppression réservée à web.php avec auth.

Voir la solution 
// routes/api.php
Route::get('/cours', function () {
    return Cours::all();
});

Tester avec curl http://localhost:8000/api/cours — aucun jeton requis, contrairement à l'exemple Sanctum de la section 04, car cette route n'est volontairement pas placée dans le groupe auth:sanctum.

06

Mini-projet final

À réaliser en autonomie ou en binôme, en réutilisant tout ce qui a été construit depuis la séance 1 — c'est le livrable final du module.

Plateforme de gestion d'une petite bibliothèque

Cahier des charges à implémenter, puis solution guidée ci-dessous.

  • Données : modèles Livre (titre, auteur, disponible) et Emprunt (livre_id, user_id, date_emprunt), avec la relation correspondante.
  • Interface web protégée : un utilisateur connecté (Breeze) peut lister les livres, en emprunter un disponible, et voir la liste de ses propres emprunts.
  • API publique en lecture seule : GET /api/livres retourne le catalogue complet, sans authentification.
  • Livraison : l'ensemble (app + base de données) démarre avec une seule commande docker compose up --build, migrations et seed inclus.
Voir la solution guidée 
// database/migrations/..._create_emprunts_table.php
Schema::create('emprunts', function (Blueprint $table) {
    $table->id();
    $table->foreignId('livre_id')->constrained();
    $table->foreignId('user_id')->constrained();
    $table->date('date_emprunt');
    $table->timestamps();
});
// app/Models/Livre.php
public function emprunts()
{
    return $this->hasMany(Emprunt::class);
}

// app/Models/Emprunt.php
protected $fillable = ['livre_id', 'user_id', 'date_emprunt'];

public function livre()
{
    return $this->belongsTo(Livre::class);
}
// routes/web.php
Route::middleware('auth')->group(function () {
    Route::get('/livres', [LivreController::class, 'index']);
    Route::post('/livres/{livre}/emprunter', [LivreController::class, 'emprunter']);
    Route::get('/mes-emprunts', [LivreController::class, 'mesEmprunts']);
});
// app/Http/Controllers/LivreController.php
public function emprunter(Livre $livre)
{
    if (!$livre->disponible) {
        return back()->with('erreur', 'Ce livre est déjà emprunté.');
    }

    Emprunt::create([
        'livre_id' => $livre->id,
        'user_id' => auth()->id(),
        'date_emprunt' => now(),
    ]);

    $livre->update(['disponible' => false]);

    return redirect('/livres');
}

public function mesEmprunts()
{
    $emprunts = auth()->user()->emprunts()->with('livre')->get();
    return view('livres.mes-emprunts', ['emprunts' => $emprunts]);
}
// routes/api.php — lecture publique, sans middleware auth
Route::get('/livres', function () {
    return Livre::all();
});
## docker-compose.yml final — reprend celui de la séance 1
## avec, en plus, la commande au démarrage qui migre et seed automatiquement
app:
  build: .
  ports: ["8000:8000"]
  volumes: [.:/app]
  depends_on: [db]
  command: >
    sh -c "php artisan migrate --force &&
           php artisan db:seed --force &&
           php artisan serve --host=0.0.0.0"

Pourquoi command plutôt que de laisser CMD du Dockerfile : ça garantit qu'à chaque docker compose up, la base est à jour avant que le serveur ne démarre — indispensable pour qu'un correcteur ou un camarade puisse lancer le projet en une seule commande sans étape manuelle oubliée.
