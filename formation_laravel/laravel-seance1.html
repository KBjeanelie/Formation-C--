02

Qu'est-ce que Laravel ?

Laravel est un framework PHP qui fournit déjà les briques dont a besoin une application web : routing, accès aux données, gestion des formulaires, sécurité, envoi d'e-mails... Sans framework, il faudrait réécrire tout cela pour chaque projet.

Laravel suit le modèle MVC (Modèle - Vue - Contrôleur), qui sépare trois responsabilités :

CoucheRôle
ModèleReprésente et manipule les données (base de données) — vu en séance 2
VueCe que l'utilisateur voit — fichiers Blade (.blade.php)
ContrôleurReçoit la requête, orchestre modèle et vue, renvoie une réponse
Pourquoi ça compte : séparer ces responsabilités évite de mélanger requêtes SQL, logique métier et HTML dans un seul fichier — un problème courant en PHP procédural classique.
03

Installation locale

Prérequis : PHP 8.2+, Composer, et une base de données (MySQL ou SQLite pour démarrer simplement).
composer create-project laravel/laravel nom-du-projet
cd nom-du-projet
php artisan serve

Le serveur de développement écoute par défaut sur http://127.0.0.1:8000.

À vérifier avant de continuer : la page d'accueil par défaut de Laravel doit s'afficher dans le navigateur.
04

Environnement Docker

Installer PHP, Composer et MySQL sur chaque machine peut vite diverger d'un poste à l'autre. Docker fige l'environnement une bonne fois pour toutes : ce qui tourne chez vous tourne à l'identique chez tout le monde. C'est cet environnement qui servira à dockeriser les TP des prochaines séances.

Dockerfile

À la racine du projet Laravel :

FROM php:8.3-cli

RUN apt-get update && apt-get install -y \
    git unzip libzip-dev \
    && docker-php-ext-install pdo_mysql zip

COPY --from=composer:latest /usr/bin/composer /usr/bin/composer

WORKDIR /app
COPY . .

RUN composer install

EXPOSE 8000
CMD ["php", "artisan", "serve", "--host=0.0.0.0"]

docker-compose.yml

Deux services : l'application Laravel, et une base MySQL.

services:
  app:
    build: .
    ports:
      - "8000:8000"
    volumes:
      - .:/app
    depends_on:
      - db
    environment:
      DB_HOST: db
      DB_DATABASE: laravel
      DB_USERNAME: laravel
      DB_PASSWORD: secret

  db:
    image: mysql:8
    environment:
      MYSQL_DATABASE: laravel
      MYSQL_USER: laravel
      MYSQL_PASSWORD: secret
      MYSQL_ROOT_PASSWORD: root
    ports:
      - "3306:3306"
    volumes:
      - db_data:/var/lib/mysql

volumes:
  db_data:

Lancer l'ensemble :

docker compose up --build

Puis, dans un second terminal, exécuter les commandes Artisan à l'intérieur du conteneur :

docker compose exec app php artisan migrate
Pourquoi ce découpage en deux services : l'application et la base de données sont deux responsabilités distinctes, avec des cycles de vie différents (on peut redémarrer l'app sans perdre les données MySQL, car elles vivent dans le volume db_data, séparé du conteneur).
Piège fréquent : dans .env, DB_HOST doit être le nom du service Docker (db), pas 127.0.0.1 — depuis le conteneur app, 127.0.0.1 désigne le conteneur lui-même, pas la base de données.
Les deux approches cohabitent : installation locale pour comprendre Laravel sans couche supplémentaire en séance 1, puis Docker devient la référence à partir de la séance 2, pour que l'environnement soit identique du poste de chaque étudiant jusqu'au mini-projet final.

06

Routing

Une route associe une URL et une méthode HTTP à une action :

// routes/web.php
Route::get('/', function () {
    return 'Accueil';
});

Route::get('/etudiants/{id}', function ($id) {
    return "Étudiant numéro " . $id;
});

{id} est un paramètre de route : sa valeur est automatiquement passée à la fonction.

07

Contrôleurs

Au-delà de quelques routes, la logique se déplace dans des contrôleurs dédiés :

php artisan make:controller EtudiantController
// app/Http/Controllers/EtudiantController.php
class EtudiantController extends Controller
{
    public function accueil()
    {
        return 'Bienvenue dans le module étudiants';
    }
}

Puis référencer le contrôleur depuis les routes :

// routes/web.php
use App\Http\Controllers\EtudiantController;

Route::get('/etudiants', [EtudiantController::class, 'accueil']);
Pourquoi un contrôleur plutôt qu'une fonction dans web.php : ça garde le fichier de routes lisible (une liste de correspondances URL → action), et regroupe la logique d'une même fonctionnalité dans une seule classe organisée.
08

Vues Blade

Un contrôleur renvoie généralement une vue plutôt qu'un texte brut :

// app/Http/Controllers/EtudiantController.php
public function accueil()
{
    return view('etudiants.accueil', ['nom' => 'Fabrice']);
}
<!-- resources/views/etudiants/accueil.blade.php -->
<h1>Bonjour, {{ $nom }} !</h1>

@if ($nom)
    <p>Compte actif</p>
@endif
Syntaxe BladeRôle
{{ $variable }}Affiche une valeur (échappée automatiquement contre les failles XSS)
@if / @endifCondition
@foreach / @endforeachBoucle
@extends / @sectionHéritage de mise en page (layouts communs)
09

Exercices pratiques

À réaliser dans l'ordre. Le dernier exercice dockerise le mini-projet construit pendant la séance.
Ex. 1

Route paramétrée

échauffement

Créer une route /salut/{prenom} qui affiche "Salut, {prenom} !" en utilisant le paramètre de route.

Voir la solution 
// routes/web.php
Route::get('/salut/{prenom}', function ($prenom) {
    return "Salut, " . $prenom . " !";
});
Ex. 2

Contrôleur Cours

facile

Créer un CoursController avec une méthode liste() qui renvoie une vue affichant un tableau PHP de 4 noms de cours passés à la vue, affichés dans une <ul> avec @foreach.

Voir la solution 
// app/Http/Controllers/CoursController.php
class CoursController extends Controller
{
    public function liste()
    {
        $cours = ['Algorithmique', 'Bases de données', 'Réseaux', 'Développement Web'];
        return view('cours.liste', ['cours' => $cours]);
    }
}
<!-- resources/views/cours/liste.blade.php -->
<h1>Liste des cours</h1>
<ul>
    @foreach ($cours as $c)
        <li>{{ $c }}</li>
    @endforeach
</ul>
// routes/web.php
Route::get('/cours', [CoursController::class, 'liste']);
Ex. 3

Layout commun

intermédiaire

Créer un layout resources/views/layouts/app.blade.php avec un @yield('content'), puis faire hériter la vue de l'exercice 2 de ce layout avec @extends et @section.

Voir la solution 
<!-- resources/views/layouts/app.blade.php -->
<!DOCTYPE html>
<html lang="fr">
<head><title>Mon application</title></head>
<body>
    <nav>Menu du site</nav>
    @yield('content')
</body>
</html>
<!-- resources/views/cours/liste.blade.php -->
@extends('layouts.app')

@section('content')
    <h1>Liste des cours</h1>
    <ul>
        @foreach ($cours as $c)
            <li>{{ $c }}</li>
        @endforeach
    </ul>
@endsection

Sans layout, chaque vue devrait répéter le même HTML de base (<html>, menu, etc.) — @extends centralise cette structure commune à un seul endroit.

Ex. 4

Dockeriser le mini-projet de la séance

défi

Reprendre le projet Laravel de la séance (routes + contrôleur + vues des exercices 1 à 3), ajouter le Dockerfile et le docker-compose.yml vus en section 04, puis vérifier que docker compose up --build permet d'accéder au projet sur http://localhost:8000/cours exactement comme en local.

Voir la solution

Étapes à valider, dans l'ordre :

  1. Placer Dockerfile et docker-compose.yml à la racine du projet (à côté de artisan).
  2. Copier .env.example vers .env si ce n'est pas déjà fait, puis adapter DB_HOST=db comme indiqué en section 04.
  3. Lancer docker compose up --build.
  4. Dans un second terminal : docker compose exec app php artisan key:generate, puis docker compose exec app php artisan migrate.
  5. Ouvrir http://localhost:8000/cours — la liste des cours doit s'afficher, servie depuis le conteneur.

C'est exactement cette base Docker qui sera réutilisée telle quelle pour les TP des séances 2 à 4, avec des services supplémentaires ajoutés au fil du cours (par exemple phpMyAdmin en séance 2).
